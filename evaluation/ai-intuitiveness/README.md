# AI intuitiveness evaluation

This is a versioned, replayable evaluation of the complete natural-language path:

```text
user wording + visible app context
→ app routing
→ locally verified calibrated outcome anchors
→ generated API request
→ isolated API response
→ app validation and feasibility
→ optional revision request/response
→ resulting UI state
→ user-centered acceptance classification
```

No generated suite data is retained in the repository. Start the next run in a new versioned directory and keep that run's `queries.json` and `contexts.json` unchanged while iterating on implementation or prompt fixes. Create a new suite version only when deliberately changing the corpus, context snapshots, response policy, or rubric.

## Files

- `suite.json`: suite identity, app build, date, and baseline note.
- `queries.json`: the exact natural-language inputs. It contains no expected answers.
- `contexts.json`: the allow-listed visible state, current plan when visible, initial UI state, and built-in catalog snapshot.
- `expectations.json`: the answer key and user-centered acceptance rubric. Never provide this file to the API-response stage.
- `generated-requests.json`: requests produced by the same core request builder used by the app.
- `api-responses.json`: one isolated response per request and any later feasibility-revision responses.
- `app-observations.json`: results recorded by passing drill responses through the real app parser and calibrated trajectory/Nova feasibility model.
- `followup-requests.json`: feasibility revision requests; `responded` says whether the corresponding next response round is present.
- `app-states.json`: the state transition produced by each response round.
- `report.json`: final acceptable/unacceptable classification using the latest completed round.
- `findings.md`: human analysis of the current run and proposed fixes.
- `model-policy.json`: default model/effort by evaluation stage, escalation rules, and single-configuration fallbacks for v1–v3.
- `quality-rubric.json`: AI-judged 0–10 response quality and 0–10 issue-severity definitions.

## Reusable procedure

1. Freeze or copy a suite version before changing code.
2. Edit only `queries.json` and `contexts.json` to define a new corpus. Keep one stable ID per query/context pair.
3. Generate the exact API inputs:

   ```bash
   node scripts/ai_intuitiveness_eval.js generate evaluation/ai-intuitiveness/<suite>
   ```

   Create/edit requests include a compact feasibility guide generated by the production trajectory/Nova model for the current saved calibration and robot pose. The guide contains only verified intuitive outcome ranges; it never exposes pose values, calibration coefficients, wheel settings, or protocol parameters.

4. Produce each API response in a clean, independent model call using the `isolatedApiResponse` configuration in `model-policy.json`. Supply only that case's `request` string from `generated-requests.json`. Do not supply this README, expectations, other cases, conversation history, app source, or prior responses. Save the raw result in `api-responses.json`, recording `model` and `effort` beside every response round.
5. Pass every create/edit response through the actual app's paste/import path. Record its feasibility report in `app-observations.json`; do not infer feasibility from schema validity.
6. Derive app states and revision requests:

   ```bash
   node scripts/ai_intuitiveness_eval.js apply evaluation/ai-intuitiveness/<suite>
   ```

7. For every unresponded item in `followup-requests.json`, repeat step 4 using only that follow-up request. Then repeat steps 5–6 until every latest drill round is feasible or the configured retry limit is reached.
8. Generate the acceptance report:

   ```bash
   node scripts/ai_intuitiveness_eval.js report evaluation/ai-intuitiveness/<suite>
   ```

   Then have an evaluator model read the saved query, visible context, generated request, response rounds, app observations, resulting state, expectation, and `quality-rubric.json`. Save one 0–10 `qualityScore` per case with a concise rationale, plus each identified issue's 0–10 `severity`. Binary acceptance remains the regression gate; the score measures degrees of quality within both categories.

   The reusable evaluator runner performs that isolated AI judgment and records its own usage:

   ```bash
   node scripts/ai_intuitiveness_eval.js quality-input evaluation/ai-intuitiveness/<suite>
   node scripts/run_ai_intuitiveness_quality.js evaluation/ai-intuitiveness/<suite>
   ```

9. Analyze unacceptable cases by stage: context construction, intent routing, API instruction clarity, API response, parsing/validation, feasibility revision, state transition, or final UX. Fix the earliest faulty stage rather than compensating later.
10. After a product change, rerun the unchanged suite and compare `report.json`, individual state transitions, follow-up count, and reasons—not only the aggregate score.
11. If problems remain, enter the remediation loop:
    - Add or retain a regression assertion that reproduces each problem.
    - Fix the earliest faulty app stage with the smallest general solution; do not change the frozen queries, contexts, or expectations merely to improve the score.
    - Regenerate every downstream artifact affected by the fix. A routing or prompt change requires fresh isolated API responses; a changed drill response or physical model requires fresh app-feasibility observations. Do not reuse stale outputs as if they came from the new request.
    - Rerun follow-up rounds and the complete report, then compare every case with the previous run to catch regressions as well as improvements.
    - Repeat until the remaining unacceptable cases are either fixed or explicitly documented as blocked, ambiguous, or intentionally unsupported.
    - Add a few neighboring phrasings when a fix could be overfitted to one sentence, while keeping the original failing case unchanged.

The objective is to reduce genuine user-facing failures over successive runs, not merely maximize the aggregate number. A change is an improvement only when the original intent is handled more intuitively without making other sensible inputs worse.

Prioritize remediation by descending estimated severity, then recurrence likelihood, then leverage across cases. Preserve each loop's inputs, outputs, acceptance report, quality evaluation, and token usage under `loops/loop-N/` before changing code or prompts.

`node ai-intuitiveness-selftest.js` verifies that the reusable evaluator surface and model policy remain available without depending on any retained sample corpus. Each generated suite is responsible for preserving its own loop/version artifacts while it is under evaluation.

## Model and effort policy

`model-policy.json` is the executable decision record for future runs. Its v1, v2, and v3 profiles assume cumulative suites of 10, 40, and 140 cases. Read it before generating responses or starting the remediation loop. Its preferred staged policy is:

- Luna/low for isolated API-role responses and deterministic/mechanical evaluation.
- Terra/medium for diagnosing unacceptable cases, changing code, and verifying general fixes.
- Sol/medium only for a concrete hard case that remains unresolved after Terra/medium.

The number of cases does not by itself justify a stronger model. Larger suites should batch the same isolated calls and selectively escalate failures. If one model/effort must perform an entire suite, use the version's `singleConfigurationFallback`; this is simpler but normally more expensive than the staged policy.

Before trusting Luna/low for a new evaluation generation, use v1 as a calibration set. Escalate the isolated response stage to Luna/medium only when Luna/low produces malformed output, violates the request's explicit contract, or changes a result for a reason attributable to response quality. Do not escalate merely because the app correctly rejects an infeasible proposal or exposes a genuine UX defect.

Each new response round must include its actual generation provenance:

```json
{
  "round": 1,
  "model": "gpt-5.6-luna",
  "effort": "low",
  "response": {}
}
```

If the named models are unavailable in a later environment, use the cheapest available equivalent role and record the substitution and reason in `findings.md`. This makes comparisons honest without tying the procedure permanently to one model generation.

## Isolation rule for the API role

The person or model producing a response must behave as a stateless API invocation. The generated request is the entire world for that response. In particular, do not use app source, prior conversation, expected outcomes, another case, previous API output, or undocumented Table Tennis Robot Studio behavior. A second-round response may use its saved feasibility-revision request because that request explicitly contains the relevant first proposal and app report.

## Scope

This evaluation covers intent routing, prompt sufficiency, structured API communication, local validation, modeled feasibility revisions, and expected UI state. It does not prove physical Nova behavior or safety. No generated response starts the robot automatically.
